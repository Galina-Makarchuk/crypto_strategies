Second full-codebase review of the `engine/` package, following
[audit-2026-06-04.md](audit-2026-06-04.md) (nine correctness fixes + a

[config-audit-and-fixes-2026-06-13.md](config-audit-and-fixes-2026-06-13.md)

## Method

The core correctness path (`core` / `backtester` / `exits` / `indicators` /
the three configurators / `config_validation`) was read by hand. The 22
strategies and the ML pipeline were swept by two focused sub-agents against the
framework's contracts. Then **every finding below was independently
re-verified against source by a separate adversarial agent** (one skeptic per
finding, told to *refute* the claim) before being recorded — the same
hand-verification discipline that produced the "claims corrected" section in
[config-audit-and-fixes-2026-06-13.md](config-audit-and-fixes-2026-06-13.md).
That pass **downgraded four findings and corrected one materially** (see §4).
File:line references are current as of this audit.

A **follow-up adversarial re-verification** (same date) re-ran one skeptic per
finding against source and independently re-checked the §1 clean claims. It
confirmed all ten original findings, **materially corrected M1** (the
`impulse_flag` long case — see §4), and **added three findings the first pass
missed**: **M4 / M5** (a sweep of all 22 strategies for the restart-amnesia
hazard turned up two more affected strategies) and **M6** (a config-validation
hole that qualifies the §1 "config layer is rigorous" claim). It also added the
inverse-contract P&L scope note in §1.

## 1. What was verified clean (the core path is sound)

The load-bearing invariant holds and the engine's historical-backtest path is
trustworthy. Specifically verified:

- **No look-ahead.** Every strategy's `on_bar` reads only `df.iloc[0..i]`; the
  backtester *enforces* it via a truncated view (`enforce_causality=True`), and
  [test_config_propagation.py](../engine/tests/test_config_propagation.py) pins
  the enforced and unenforced runs identical. All `prepare()` precomputation is
  causal (the swing/level pivot masks, the HTF resamples, the ML feature frame —
  the last confirmed by an exhaustive per-bar diff with max leak `0.0`).
- **Inversions are true direction flips**, and every delegating strategy follows
  `update_peak → check exit → check entry` with the trailing stop tracking
  `Trade.peak_price`, not the previous close.
- **Config layer is rigorous** *(with one hole — see M6)*. Import-time guards
  (`_validate_params_registry` / `_validate_exit_catalog`) pin that every
  `StrategyName` has a params class and a valid exit; a foreign *numeric* knob
  raises `TypeError`; validation is centralized in
  [config_validation.py](../engine/config_validation.py). The exception M6
  records: `TradingConfig`'s two **enum** fields (`sizing_mode` / `direction`)
  are not validated, so a raw-string override slips through silently.
- **State machine + P&L** in [core.py](../engine/core.py), the equity layer's
  zero-floor, the daily-loss / direction / max-holding overlays, and the
  data-cache (atomic parquet write + provenance sidecar + contract re-assertion)
  are all correct.
- **Scope note — P&L is linear quote-currency math only; there is no
  inverse-contract model.** `PositionState.exit()` computes `(price − entry) /
  entry` in bps for *every* trade regardless of `--category`. `inverse` is only
  a Bybit product-type selector for **fetching**
  ([fetcher.py](../engine/fetcher.py)); the `*_inv` strategies merely flip
  signal direction — neither touches the payoff formula. Real inverse perpetuals
  are coin-margined, so their quote-currency P&L is **non-linear** in price (it
  curves with `1/price`); an inverse backtest here therefore carries a modeling
  simplification. It is self-consistent across backtest and live (no train/serve
  skew) and is **by design / out of scope** for a correctness pass — noted here
  only so the "P&L … correct" claim above is not read as "inverse contracts are
  modeled."

The findings below are **not** in that path — they cluster in the three places
the prior audits left open: **live-mode restart fidelity, ML
cross-validation hygiene, and configurator-vs-evaluation consistency.**

## 3. Relationship to the deferred items in audit-2026-06-04

**H1, M1, M4 and M5 are the concrete symptoms of the architectural limitation
already noted in [audit-2026-06-04.md](audit-2026-06-04.md) §3** ("Live cross-bar
strategy state is wiped each tick") — still unfixed.

In live mode `prepare()` runs **fresh every tick** and `on_bar` runs **only on
the last bar**, while `LiveRecords` persists the *position* but not the
strategy's runtime scratchpad (`_entry_bar_idx`, `_active_target`, `_t2`,
`_t1_hit`, the adaptive regime flags `_entry_trending` / `_entry_follow`, …).
Two consequences fall out of that one design:

1. **Restart amnesia (H1, M1, M4, M5).** A restored position wakes up with its
   scratchpad reset to defaults — for `exhaustion_reversal` the `-1` entry-bar
   marker makes the bar-index time-stop fire instantly; for
   `order_block`/`impulse_flag` the `0.0` target is forgotten (stop survives,
   take-profit does not — and `impulse_flag`'s T1 check misfires on a restored
   long, see M1); for `supertrend_adaptive`/`ema_adaptive` the lost entry-regime
   flag inverts the native signal-flip exit (M4/M5).
2. **Stateful setups can't accumulate live.** Because the scratchpad is wiped
   each tick and only the newest bar is examined, multi-bar build-ups
   (impulse → wait → flag → breakout) never accumulate, so these strategies
   effectively **can't open new structural trades in steady-state live**.

**Durable fixes:** (a) persist/rebuild the strategy scratchpad on restore (or
run `prepare()` incrementally across the live window), or — narrower, for the
lost target only — (b) re-derive the target from data that *is* persisted:
`target = entry ± RR × |entry − stop|`, using the restored `Trade.stop_price`
and the strategy's R:R config. Both are out of scope for a review pass.

Live mode is **paper / forward-test (no real orders)**, so today these corrupt
the simulated track record after a restart, not real money — but they become
must-fix the moment live is wired to place orders.

The other deferred item — [audit-2026-06-04.md](audit-2026-06-04.md) §2, the
ML training-notebook leakage — is **separate from M2 here**: §2 is leakage in
how the notebooks *produce* the injected probabilities; M2 is a distinct,
engine-side under-purge in `PurgedKFold` itself. Both point at the same risk
(optimistic OOS/CV metrics in the ML research path) and both leave the engine's
backtest path untouched.

## 4. Claims corrected / downgraded after verification

The adversarial re-verification changed the following from the first-pass
report (recorded here for honesty, matching
[config-audit-and-fixes-2026-06-13.md](config-audit-and-fixes-2026-06-13.md)'s
convention):

- **L1 (evaluation default) — downgraded MEDIUM → LOW; impact claim retracted.**
  The first pass claimed the notebooks call `sweep`/`walk_forward` *without*
  threading `trading_config`, so an edited `ACTIVE_TRADE` would be silently
  ignored. **That is false** — it came from a single-line grep that missed the
  notebooks' multiline calls. A programmatic scan of every notebook found that
  all standard notebooks define `TRADING_CONFIG = ACTIVE_TRADE` and pass it into
  every `walk_forward`/`grid_search` call (0 omissions). The code-level facts
  (bare-`TradingConfig()` defaults; `grid_search` internal inconsistency) are
  real, but the harm is only a direct-caller API asymmetry, not user-facing
  config loss.
- **M2 (PurgedKFold) — downgraded HIGH → MEDIUM.** Real and unguarded, but
  PurgedKFold is wired only into the two `swing_ml*` notebooks (at
  `embargo=100`, not the default 24), so the magnitude is smaller than the
  first-pass figure and the blast radius is research-only CV inflation, not the
  engine runtime.
- **L2 (swing same-bar re-entry) — downgraded MEDIUM → LOW.** Conditional
  (needs the entry predicate satisfied on the same bar), intentional/documented,
  and suppressible via the existing cooldown knob; a backtest-realism nit, not a
  state-machine bug.
- **L3 (order-flow z-score) — downgraded MEDIUM → LOW.** Confirmed, but the
  distortion is concentrated at day-edges / missing days (not scattered no-trade
  bars), train/serve is self-consistent, and the effect is clip-bounded.

H1 (exhaustion restart) and M3 were confirmed exactly as stated.

The **follow-up re-verification pass** then changed the following:

- **M1 (order_block / impulse_flag restart) — core mechanism confirmed, but the
  `impulse_flag` long case corrected.** The first pass wrote that `impulse_flag`
  "reverts to the wider original stop." That is true only for **shorts**. For a
  **long**, the inverted T1 check `high_i ≥ _t1` with the re-zeroed `_t1 = 0.0`
  is trivially true on the first post-restart tick, firing a *spurious*
  breakeven-shift that **tightens** the stop to entry — a long can be
  force-stopped at its own entry price, the opposite of a wider stop. Also
  corrected: the 0.0 target is rejected in `_Target.evaluate`
  ([exits.py:193-194](../engine/exits.py#L193-L194)), not at the originally
  cited `exits.py:169` (which is the *stop*-survival fallback, and does survive).
- **M4 / M5 added — the restart-amnesia enumeration was incomplete.** A sweep of
  all 22 strategies for the exact hazard (instance state mutated in `on_bar`,
  reset by `prepare()`, not persisted by `LiveRecords`, consequential to a
  *restored open trade*) found two more affected strategies the first pass
  missed: `supertrend_adaptive` and `ema_adaptive`, whose entry-regime flag is
  lost on restart and inverts the native signal-flip exit. The remaining
  strategies are clean for restored-trade exits (`swing_*`'s `_last_exit_bar`
  only gates the re-entry cooldown; `level_*`/`fractal_*` recompute levels in
  `prepare()` and exit off the surviving `Trade.stop_price`).
- **M6 added — the "config layer is rigorous" clean claim has one hole.** An
  independent config-layer hunt found that `TradingConfig.__post_init__`
  validates every numeric field but neither of its two **enum** fields, so a
  raw-string `direction` / `sizing_mode` override is silently accepted and (for
  `direction`) yields a zero-trade backtest with no error.

4. **H1 / M1 / M4 / M5 (live restart fidelity)** — *done at the root.* Rather

None of these touch the historical-backtest correctness path itself (M6 is

## 6. Resolution (implemented 2026-06-13)

The audit pass itself was review-only; the fixes below landed immediately after,
in the same commit as this doc. `pytest engine/tests/` → **248 passing**.

- **H1 / M1 / M4 / M5 (live restart fidelity).** The live tick now rebuilds its
  position by **replaying the strategy over the whole candle window from a fresh
  state each tick** — the backtester's own loop minus the end-of-data
  force-close — so a restored or continuing position is managed with
  correctly-rebuilt internal state. This is the durable fix from §3(a), and it
  also resolves §3's *second* consequence (stateful setups could not accumulate
  in steady-state live). Trade ids are now deterministic (entry-bar + side) so
  the per-tick dedup is stable across ticks/restarts. A window guard warns if an
  open position is held longer than the candle window. [live.py, core.py]
- **M2 (PurgedKFold).** Added a `purge` parameter (feature-window purge); both
  `swing_ml*` notebooks now pass `purge=200` (the `vol_200` lookback). [ml/splits.py]
- **M3 (write amplification).** Only newly-closed trades are persisted per tick
  (dedup by stable id) — no full-history re-save. [live.py]
- **M6 (enum validation).** `TradingConfig` now validates `sizing_mode` /
  `direction`; a raw-string override fails at construction. [trade_configurator.py,
  config_validation.py]
- **L1** evaluation defaults to `ACTIVE_TRADE`. **L2** swing cooldown defaults to
  1, blocking same-bar re-entry (golden regenerated). **L3** order-flow rolling
  features are derived on the kline grid. **L4** SuperTrend seeds the trend by
  backfilling to the first band break. **L5** the CLI dispatch dict is guarded at
  import. **L6** `ret_k_atr` is now a clean ATR-normalized return.
